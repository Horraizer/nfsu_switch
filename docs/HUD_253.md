### Font correction after console feedback

Gear/speed use `LCD_LET48`, hash `0xBBBA71C2`. MPH now uses
`CONDUITMDITC_TT14I`, hash `0x5B9D84DB`, the thinner italic letterforms
supported by `retail-01.webp` and `retail-02.webp`. The previous
`FONT_CONDUITMDITCTT38BI` choice was a wrong screenshot fit. Runtime
selection of the units font has not been fully traced; the family choice
remains a reference-supported inference. In particular, the FEng `OP`
payloads are raw fields, not established font indices.

`tools/hud253_trace.py` now exports selected glyph metrics from the
`0x00030201` chunks in `Languages/English.bin`. That input's SHA-256 is
`6CBAB64235523149B95966B1844CDCA9FB858744126F8D9AD10E72C921AB8790`.
The `FNTF` signature is after the two 256-byte names; glyph count is at
`FNTF+10` and the 16-byte record array begins at `FNTF+128`. Records hold
width/height at `+2/+3`, atlas x/y at `+4/+6`, signed bearings at `+9/+10`
and signed advance at `+14`. The trace checks the input identity, chunk
bounds and record-layout flag before reporting them.

The complete glyph function `0x004F4790..0x004F48A7` samples a one-texel
border around each glyph while its quad uses native width/height and signed
bearings. The string renderer `0x004F48B0..0x004F4CF2` advances the pen by
the record's `+14` field at `0x004F4C22`. The HUD now follows those rules
instead of treating glyph widths as advances or fitting a common ascent.
This matters for narrow `1`, overlapping LCD strokes, neutral/reverse, and
multi-digit speed. Right alignment at the SAD position matches the original
stock captures; SAD supplies the gear, speed and units scales.

`nfsu_race_hud_tests` pins the recovered UVs, bearings, right alignment and
proportional spacing, including `100` and both presentation sizes. It also
checks unchanged needle/telemetry behavior. `tools/hud253_font_evidence.py`
produces common-scale original/before/after crops, owner-before crops and
input identities with reproducible threshold measurements. The original
orange gear is measured separately from the port's blue gear. Small raster
edge differences remain under JPEG/antialiasing and nearest CPU sampling;
these observations do not establish exact original pixel equivalence or
GPU equality. MPH still approximates speed from horizontal velocity
magnitude because the port has no recovered retail car `+0x3D4`.

## RPM consumer, timing and remaining dependency

The HUD procedure `0x004A0F50` reads car `+0x3E0` at `0x004A0FAF`, unless
the debug global `0x007000E4` overrides it. It calls `0x004A0EA0` at
`0x004A1049`, using max RPM from the setup block. The mapping clamps
engine/max to 0..1 and uses rotation 44..215 below 9000, 50..210 for
9000..9999 and 45..225 from 10000. The screen shaft angle is 270 minus
that rotation. This mapping was already correct and remains unchanged.

`0x004757D0` derives engine RPM from wheel spin, selects gear and clamps
RPM to idle/max. `0x00474A60..0x00474A79` exports engine `+0x120` and gear
`+0x124` together to car `+0x3E0` and `+0x3D8`. Integration at
`0x00474A90` completes its substep loop before calling that export path at
`0x00474C53`. These are static producer/consumer edges; the HUD's scheduling
relative to presentation in a running original game is not measured.
The separate speed-synthesized RPM helper `0x00427A30` has a 50-RPM slew
path; its existence is not evidence for adding that animation to the player
HUD, which consumes the exported engine field.

The port commits engine RPM and gear in the same `VehicleModel::step`.
`RaceSession` does two 120Hz physics steps per driving 60Hz tick. Desktop
capture and Switch presentation build the HUD after the completed race tick.
`RaceHudFrame::readout` records the exact state that generated the submitted
needle vertices. Focused tests cover manual up/downshifts, stale wheel-RPM
inputs, frame reuse and both presentation scales. No stale HUD state was
found. The 60Hz audit is a presented-state table, not a dump of each 120Hz
substep; countdown ticks can have physics step zero.

At `0828215`, the attached event1 audit at tick 5449/5450 (physics step
10572/10574, simulation time 90.816667/90.833333s) records engine RPM
6467.478 -> 4314.512, gear slot 2 -> 3 (displayed 1 -> 2), rotation
182.242 -> 136.223 degrees. The next samples rise again, then tick 5468
returns to first gear, 18 displayed ticks after the upshift. The drop,
subsequent rise and downshift all exist in the committed simulation state.
They are not created by needle interpolation or cached HUD telemetry.

Named dependency `HUD253_ENGINE_SHIFT_PARITY`: obtain original frame/RPM
sequences for matched stock upshift/downshift and decide whether engine
coupling or automatic shift hold differs. Existing approximate clutch/slip
feedback and shift hold are documented in [HANDLING_GAPS.md](HANDLING_GAPS.md).
This PR changes no physics and does not claim that the owner's complete
temporal complaint is solved. Original sequence/runtime evidence was absent.

Named dependency `HUD253_GEAR_FLAG`: `0x004A112A` reads car `+0x3E8` and
selects blue `0xff0080c0` when nonzero, orange `0xffff8040` when zero.
The producer semantics are unresolved. Do not invent a threshold on speed,
RPM, gear or shift state to imitate an idle still. The port retains blue.
